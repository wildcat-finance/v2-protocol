# R2 plan: default and repayment implementation foundation

- Status: planned; implementation has not started.
- Starting source: `7038b5aa3f035355c773430eac1c24047bd4d7d7`.
- Contract: [P-01 draft](./v2.5-tranching-preparation.md).
- Progress: [tracker](./v2.5-tranching-preparation-r2-tracker.md).
- Resume after the requested maintenance pause. Start with R2-01.

R2 closes the short product decision register, fixes the implementation ABI and
boundary rules, and proves that the core design can deploy within the actual
stored-initcode limit. It then lands the creation plumbing and default tracker
as reviewed checkpoints. A size failure changes the implementation plan before
the full dated-accounting feature is built.

This plan does not authorize silently choosing an unconfirmed product rule.
Routine implementation choices follow the spec's recommendations and measured
evidence. No tranche vault or tranche policy is implemented here.

## R2-01: Settle the working model and interfaces

- Resolve P-01 through P-04 in the spec, recording selected behavior rather than
  turning the other-session handoff into blanket approval. Do not reopen the
  confirmed marker or collection requirements.
- Lock the cure/deadline equality rule, including the simultaneous 90-day case.
- Select marker representation, creation/getter/event ABI, storage layout,
  configuration authority and unsupported execution-callback treatment.
- Write worked accrual/cash timelines for ties and delayed processing. State
  exactly what is observed at a successful write and what is historical.
- Record intentional differences from the hook-refactor baseline, including
  execution-hook dispatch; retain the existing suite as regression evidence.

Done when the spec has no unselected product rule hidden in an implementation
task and the initial public/storage contract is concrete. This task may be a
documentation checkpoint without Solidity changes.

## R2-02: Build and measure the representative core slice

- Prototype terms/default storage, the shared dated-boundary calculation,
  historical asset handling, necessary action/withdrawal gates and emitters.
- Include the revolving override, both APR paths and the core reserve floor.
  Include enough real behavior to expose byte cost; do not count empty stubs
  as proof that the full feature fits.
- Measure deploy-profile runtime and stored-initcode size for both models and
  affected hooks. Deploy through both actual factories with the selected ABI.
- Compare matched source sets/toolchain settings. Record any estimated cost
  separately from compiled measurements and identify omitted work.

Done when the representative slice deploys with a justified remaining budget,
or a concrete alternative is reviewed. Keep a prototype explicitly labelled;
it is not a qualified production implementation or a reason to delete behavior
to meet the limit. Stage any Solidity prototype for review before committing.

## R2-03: Land creation terms and public surfaces

- Add enabled/disabled terms through structs, both factory temporary payloads,
  market construction and `onCreateMarket`; verify every assembly size/offset.
- Enforce structural checks in the core and selected product limits in supported
  templates. Cover a permissive/malformed hook in constructor safety tests.
- Add static callback-safe getters and selected factory terms event. Integrate
  fixed maturity validation and authority-transfer invariants.
- Apply the selected execution-capability configuration rule so deployments do
  not advertise a callback the new core will ignore.

Done when real factory creation covers all six combinations, invalid encodings,
zero/disabled distinctions and the chosen limits. Intermediate checkpoints must
be clearly marked incomplete P-01 and not release-ready.

## R2-04: Land the independent default marker and run tracker

- Track the selected penalized episode without repurposing `timeDelinquent` or
  changing ordinary interest splits. Observe cures at the selected checkpoints.
- Latch the marker/event once with the correct historical timestamp, retaining
  it through cure, close, authority transfer and later causes.
- Cover ordinary no-date markets as well as enabled terms. The tracker must
  compose with the dated force-penalty regime selected for the core slice.
- Preserve existing economic/permission behavior except the explicitly selected
  collection guarantee; do not change it merely because default is recorded.

Done when threshold/equality/cure tests, a focused stateful property and the
existing relevant regression suites pass. Separate marker mechanics from final
repayment-deadline satisfaction logic, which is integrated in R3.

## R2-05: Qualify the milestone and prepare R3

- Reconcile the production changes against the size prototype. Retain measured
  sizes, actual deployment results and the list of remaining code cost.
- Run checks appropriate to the landed checkpoint and all three canonical full
  test configurations before milestone completion. Report baseline lint issues
  accurately; do not manufacture new passing counts by changing discovery.
- Update the spec/tracker and prepare the R3 plan from the final R2 source.
- Present the signed task commits and milestone evidence for user review/push.

R2 completes the foundation, not tranching preparation as a whole. No deployable
partial checkpoint should be described as feature-complete.

## Workflow

Use task-sized checkpoints signed as `kethcode <dave@wildcat.finance>`.
Solidity edits, including tests and prototypes, are staged for user review
before commit. Documentation-only checkpoints may be committed as authorized.
The user reviews and pushes at milestone boundaries. No autonomous push.

Keep one production implementation of the selected behavior. Temporary prototype
code may live in an isolated checkout or clearly labelled test fixtures; do not
ship a parallel lifecycle implementation alongside the integrated core.

Follow [CONTRIBUTING.md](../../CONTRIBUTING.md),
[TESTS.md](../../TESTS.md) and the [test guide](../../test/README.md). The full
milestone/final commands are:

```sh
forge test
yarn test:fixed
FOUNDRY_PROFILE=deploy forge test
```

Use focused suites during implementation. Do not rerun unchanged full suites
for documentation-only work. Keep the user-owned PDFs, lifecycle sketch and
voice guide uncommitted. Final cleanup removes these three working documents
and their temporary index entry after an external export has been verified.
