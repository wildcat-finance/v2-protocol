Tests, docs, mocks, scripts, schemas, and deployment UI are review evidence,
not part of the contract source boundary. If deployment tooling is commissioned

## Trust and authority

| Actor or dependency | Authority or assumption |
| --- | --- |
| Borrower | Credit risk; may draw assets and use only the configuration powers granted by market and hook terms |
| Lender or arbitrary caller | Untrusted; permissionless entrypoints must not grant discretionary borrower, hook, provider, or registry authority |
| ArchController owner | Admits factories and controllers and maintains registry policy |
| SphereX admin, operator, and engine | Select and operate transaction checking and registered-sender state |
| Factory or template fee authority | Selects templates and terms for new markets and can push permitted fee-rate changes |
| Hook administrator | Controls mutable hook policy, separately from market borrower and provider administration |
| Provider administrator or provider | Controls the credentials and capabilities assigned by the hook configuration |
| Fee recipient | Receives immutable-market-recipient protocol fees after collection |
| Underlying token | Must provide stable supported ERC-20 transfer and metadata behavior |
| Sanctions sentinel and external list | External liveness and classification dependency for sanctions-gated paths |
| Hook, provider, and token callbacks | Potentially adversarial external calls; market and factory reentrancy boundaries must hold |
| Legacy wrapper factory | Trusted generation-routing dependency for markets that do not declare V2.5 floor rounding |

A market permanently trusts its selected hook address, callback flags,
underlying asset, sanctions sentinel, and immutable fee recipient. Listed assets
and external sanctions dependencies must satisfy
[security assumptions](../security/assumptions.md).

State refresh, withdrawal execution and bounded processing, wrapper creation,
and execution of a ready periodic APR reduction are permissionless. That
permission does not include choosing terms or recipients outside the already
committed state.

The current 14-item baseline neither deploys nor approves a borrower-account
factory. Approval of one introduces the additional boundary described in
[known limitations](../security/known-issues.md#dormant-borrower-account-factory-surface).

## Core properties

The review should independently test these properties rather than treating the
existing suite as proof:

1. Scaled supply, lender balances, pending withdrawals, reserved assets, and
   protocol-fee liabilities remain conserved through accrual and rounding.
2. Withdrawal batches settle in FIFO order, never reserve more underlying than
   they can attribute, and remain executable after closure when fully funded.
3. Standard and revolving accrual split correctly at batch expiry. Revolving
   markets charge the commitment fee on full supply and base APR only on the
   intended drawn portion.
4. A revert after a hook callback rolls back both market and hook state.
5. Factory CREATE2 salts, transient constructor parameters, predicted hook and
   market addresses, borrower identity, and registry writes cannot be spliced
   across callers or reentrant callbacks.
6. Borrower transfer changes only the intended operational identity and does
   not transfer hook administration, provider authority, or historical debt.
7. Wrapper deposits, withdrawals, redemptions, sanctions escrow migrations,
   and generation routing cannot create unbacked shares or consume the scaled
   backing owed to outstanding shares.
8. Every mutable privileged path has the documented caller, target set, and
   SphereX behavior; engine rotation cannot leave origination half-migrated.
9. Pagination, batch processing, closure, and registry propagation have an
   explicit bounded operational path where their full path grows with state.

Accepted behavior and representation limits are collected in
[known limitations and accepted behavior](../security/known-issues.md). A path
that exceeds those stated effects remains in scope.

## Verification commands

Run from a clean recursive checkout of the candidate with Foundry `1.7.1`:

```sh
git submodule update --init --recursive
FOUNDRY_PROFILE=default forge build --force src
FOUNDRY_PROFILE=default forge test
FOUNDRY_PROFILE=default yarn test:fixed
FOUNDRY_PROFILE=deploy forge test
FOUNDRY_PROFILE=deploy forge build --sizes src
yarn lint:check
yarn inventory:contracts --release v2.5 \
  --ref af33a82690c7935e23cd0a988a0b9133c5359614 \
  --artifacts out --output docs/releases/inventory/v2.5.json --check
```

`yarn test:fixed` pins block timestamp `1724284800` and fuzz seed `0x5eed`.
Foundry runs 1,000 cases per fuzz test and 2,000 runs at invariant depth 30.

The repository currently has a formatting-baseline failure under
`yarn lint:check`; it affects the same 40 files on the release base and the
candidate. Do not silently format the release to make that gate green. Record
the waiver or review a dedicated formatting-only diff.

Foundry can also print a non-fatal post-compile `unresolved symbol locals`
diagnostic for the SphereX modifier at
`src/spherex/SphereXProtectedRegisteredBase.sol:149`. The compiler and test
process still exit successfully. Treat any nonzero command status as a failure.

The final handoff must add a dated verification receipt. For each command,
record the exact commit, tool version, exit status, suite and test counts where
applicable, and a digest of the retained output. A command list by itself is not
evidence that the freeze candidate passed.
